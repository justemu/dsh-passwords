Development dependencies declare `>=0.2.0-alpha.0 <0.2.1-0` (the `0.2.0` patch from `alpha.0` up to but excluding the `0.2.1` line: alpha, beta, and rc prereleases plus the stable `0.2.0` release) and the shrinkwrap locks the resolved tree to the published `0.2.0-rc.1` packages, so TypeScript resolves the current public plugin APIs without drifting into a later 0.2.x patch or back to the retired `0.1.7` head. npm has published no `0.2.0` alpha/beta package, so that acceptance is a declared SemVer bound rather than a run -- the rc.1 subtree is the only `0.2.0`-line target actually installed and exercised, and no alpha build has passed full gateway acceptance. ## Plugin surfaces

| Surface | Status | Requirement |
|---|---|---|
| HTTP UI/API plugins | Code-level compatible | The gateway removes only its own authentication cookie and preserves plugin cookies; local regression and test-server lifecycle/provider flows cover the official UI/API path and generic third-party boundary. |
| Plugin combo URLs | Regression-tested | `/plugins/??...` query bytes, including the second `?`, remain unchanged; covered by the version-agnostic regression suite. |
| Plugin business `token` query | Regression-tested | Only the alpha index launch-token context strips bare `token`; plugin paths retain it. |
| Runtime-registered extension endpoint (HTTP or Remote) | Generic direct pass-through | The DSH host reports loaded extension namespaces, Remote streams, and registered routes through one runtime manifest. Subusers do not need endpoint registration or `allow_ssh`; ordinary workspace/session authorization still applies. HTTP and Remote mux extension surfaces are forwarded generically; the manifest adds identification and revocation, not a path allowlist. Subuser WebSocket upgrades follow the separate fail-closed row below. The manifest contains no extension-specific field or path protocol. |
| Registered host/SSH endpoint | Owner-only | `MCP_GATEWAY_SSH_ENDPOINTS` marks host capabilities as owner-only on HTTP, WS and matching Remote API streams. Legacy `allow_ssh=true` never grants a subuser access. |
| Ordinary extension paths outside the runtime manifest | Generic direct pass-through (HTTP and Remote) | Ordinary `/api` / root-level plugin HTTP requests and Remote mux logical streams are forwarded generically even when they are absent from the manifest. Only the hard-denied host namespaces below and object-level session/workspace authorization restrict them. The pinned rc.1 host namespaces productAnalytics, pluginRegistryProbe, and optional speech are blocked for subusers. The gateway does not guess extension names, fields, upload headers, or route semantics. |
| Ordinary extension WebSocket paths | Runtime-manifest gated | For subusers, WS upgrades are allowed for official event channels and loaded ordinary extension routes in the runtime manifest. Unknown routes return `404`, registered host/SSH routes return `403`, and owners remain unrestricted. |
| Sensitive host capabilities | Independently controlled | Official terminal, registered SSH/host endpoints, host code execution, plugin management, host telemetry, registry probing, optional speech and native host actions remain outside generic extension pass-through. DSH currently exposes no verified generic SSH capability marker for arbitrary third-party plugins: an unregistered plugin with an unknown namespace cannot be automatically identified as SSH without per-plugin rules. |
| Alpha Remote mux, subuser `workspace/follow` and `session/control` | Code-level compatible | Gateway applies resource filters; local frame tests and test-server lifecycle/multiuser concurrency probes validate the baseline flows. |
| Alpha.1 `workspaceFiles/changes` | Subuser path-scoped | HTTP unary is fail-closed. Remote subscriptions require an authorized session scope and an in-workspace target; `ready/change` frames are validated and out-of-scope absolute paths are dropped without closing the carrier. |
| Alpha Remote mux, subuser `session/follow` and `$events` | Regression-tested | `session/follow` accepts ordinary and subagent addresses; parent access is required, child grants are not; `$events` retains current correlation filtering |
| Official terminal | Owner/admin pass-through; subuser unavailable | Owner terminal HTTP unary methods and Remote mux streams pass through without SSH registration. For subusers, `list/environment/shells/close` return local no-capability UX stubs, other terminal RPCs return 403, and mux terminal streams return per-stream `terminal/unavailable`; historical `allowSsh=true` does not override this boundary. |
| Official `job` / `account` RPCs | Subuser-compatible with scoped limits | `job/list` and `job/follow` are Remote streams bound to an authorized session; only jobs whose owner matches that session are returned, and `job/kill` is session-scoped. `account/getState`, `getProfile`, `getBalance`, and `account/watch` retain the official read-only host account view under the selected function-first policy. Unknown/future unary account methods and `startSignIn`, `cancelSignIn`, and `signOut` are denied for subusers. |
| rc.2 `schedule` RPCs | Subuser-compatible with session scope | `list`, `history`, `update`, and `delete` require an authorized session ID. The global `catalog` response is filtered to authorized sessions for subusers; owners receive it unchanged. |
| Workspace ordering | Subuser-compatible with scoped limits | `workspace/insertBefore` waits for the filtered workspace/session baseline when needed; `insertSessionBefore` requires an authorized session in the requested workspace. Success responses are scoped to that same workspace and filter IDs to the caller's visible resources. Ordering is the host DSH registry's global order (not a per-user private order), so an authorized subuser can affect the shared order just as the owner can. |
| Dynamic Cordis runner | Subusers fail-closed | The complete `dynamicCordisRunner` namespace is blocked for subusers, including `runHostHalf`, runner inventory/control methods, known diagnostic methods, namespace roots, and unknown/future methods. This prevents a session-scoped request from reaching host-side dynamic package execution; owner/admin behavior is unchanged. |
| Directory picker | Official browse interaction for all users | The dsh-passwords bundle overrides DSH's platform-adaptive `directory-picker` row with the official `dsh-host-directory-picker-browse` and `dsh-client-ui-directory-picker-browse` pair. This prevents Windows loopback hosts from opening a host OS dialog that remote browsers and subusers cannot use. Both owners and subusers use the web directory list; subuser `list/createDirectory` remains constrained by gateway path authorization, while host `directoryPicker/pick` stays blocked for subusers. |
| Connection Cookie bridge | Test-server verified | `patch status` shows `patched` or `native`; the gateway refuses startup when the bridge is unavailable. The released 2.7.5 test-server deployment (DSH `0.1.7-rc.2`) reports `patched`. |

## Pinned rc.1 baseline

DSH `0.2.0-rc.1` is the bundled Docker target for the 2.7.6 working tree and the current dependency pin for the `0.2.0` line, and the only `0.2.0`-line identity published on npm so far -- so the declared `>=0.2.0-alpha.0 <0.2.1-0` dev range resolves and locks to it, while the earlier alpha/beta identities stay unproven in practice until npm publishes them. The runtime gate accepts stable `0.1.7` and prerelease identities such as alpha, beta, and rc, while rejecting unknown release lines. The rc.1 official-registry dependency tree is locked locally and the released 2.7.5 test-server deployment reports healthy health/readiness and patch status. The E2E suite completed with 128 PASS, 0 FAIL, and 9 classified INCONCLUSIVE upstream/protocol cases.

## Lifecycle contract

For the pinned DSH `0.2.0` line target (currently `0.2.0-rc.1`) and the supported DSH `0.1.2`, `0.1.3`, `0.1.5`, `0.1.6`, and `0.1.7` boundaries, gateway startup is fail-closed: the settings host-mode patch and authenticated Cookie bridge must both be present. Missing settings exits with code `35`; a missing or unsupported bridge exits with code `33`; an invalid or unknown DSH release line exits with code `37` before patching. Codes `1`, `30`, `31`, `32`, `33`, `34`, `35`, `36`, and `37` are permanent startup failures and are not retried by the host plugin. The version gate covers stable `0.1.7` and SemVer prereleases such as alpha, beta, next, rc, and build metadata, while rejecting `0.1.8` and `0.2.1`; local CLI tests cover supported variants and rejection paths.

Run `dsh-passwords uninstall` before removing the package directory or running `npm uninstall`. It removes only the `dsh-passwords` link and bundle item from the selected web profile, then rolls back only matching hash-protected patches. It leaves `.env`, `data/`, databases, certificates, and unrelated plugins unchanged. If profile dependency reconciliation or patch rollback fails, it restores the original `package.json`, `pnpm-lock.yaml`, and `node_modules` materialized state. The no-DSH case uses stable exit code `34`, independent of `LANG`; the pinned rc.1 patch and failure paths are covered by local CLI tests, and the released alpha.2 (v2.7.4) test-server patch/health checks passed. Browser rendering remains a manual acceptance boundary.
